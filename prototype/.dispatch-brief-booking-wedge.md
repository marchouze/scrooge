## Symptom (reproduced)
On `main` @ `6be949ae`, a single FX trade booking wedges the entire dashboard server (single-threaded Bun). Repro:
```
curl -s -m 120 -X POST http://localhost:3010/api/trades/book -H 'Content-Type: application/json' \
  -d '{"productType":"fx","provenanceMode":"simulated","currencyPair":{"base":"USD","quote":"ZAR"},"side":"buy","notionalAmount":1,"notionalCurrency":"USD","rate":18.5,"settlementDate":"2026-06-03","counterpartyName":"Demo Counterparty","traderRef":"sim:counterparty-fx-request"}'
```
→ hangs the full 120s (http 000). **After it, `GET /api/version` also hangs** — confirming the event loop itself is blocked, not just the booking request. The sim-hub `counterparty-fx-request` fire path hits the identical code and wedges the same way (it routes through `bookFxTrade`).

## What I've already established (start here, don't re-derive)
- **Not #910, not the sim.** Both are exonerated. `MarketDataStore.query/getLatest` are trivial indexed SQLite. The FX-sim rate path has a fallback. The wedge is in the **booking → GL → accounting cascade**.
- `bookFxTrade` (`dashboard/trade-book-view.ts:1061`): validates → `eventStore.append(tradeEvent)` (line 1225) → `await beaGlPostingEngine(ctx)` (line 1238).
- `beaGlPostingEngine` (`runtime/agents/bea-gl-posting-engine.ts:252`) replays ~30 event types (all indexed — `idx_events_type` exists, so the replays themselves are NOT the cost) and emits `SubLedgerPostingEmitted`.
- **The cascade is the cost.** In the ~10-min window around a booking the store gained: `SubLedgerPostingEmitted`, `AccountingPeriodClosed`, `TrialBalanceSnapshotted`, `CalculationPerformed`×10, `RecordFiled`×15, `SubstrateAlert`×5. Something downstream of the trade append (an append-triggered subscriber / bus handler / projection, or the GL engine itself) is running a **full period-close / trial-balance / calculation pass synchronously on the request thread**, and at 123k events that pass blocks the loop for minutes.
- Event store: 123,885 events; `FxTradeExecuted` 691, `SubLedgerPostingEmitted` 3930.

## Your job
1. **Root-cause precisely** which synchronous step in the `bookFxTrade → beaGlPostingEngine → (subscriber cascade)` chain blocks the loop, and for how long. Confirm whether it's: (a) the GL engine processing a large unposted backlog inline, (b) an append-triggered subscriber (bus/projection) firing period-close/trial-balance/calculations synchronously per booking, or (c) both. Instrument with timing; don't guess. (Tip: add coarse `performance.now()` spans around `append`, `beaGlPostingEngine`, and any bus/subscriber tick, run one booking, read the spans.)
2. **Make trade booking non-blocking and bounded.** A single trade booking must return in well under a second and must not run the institution's accounting close inline. Options to weigh (pick what's correct, not just expedient):
   - Scope `beaGlPostingEngine` to the **triggering trade's own events** when invoked from the booking path (post only the new trade's legs; keep full-replay behaviour for explicit backfill/cron runs). The current "replay ALL for idempotency" design is O(store) per booking — that's the anti-pattern.
   - Move the period-close / trial-balance / calculation cascade **off the synchronous request path** entirely — it should run on the normal derive/cron cadence, never per-trade-booking inline.
   - Ensure no append-triggered subscriber does a full-store replay synchronously on every append.
3. **Preserve correctness.** GL postings for the booked trade must still be produced (idempotently), manual-form booking must still show its GL result, and the recon gates that assert posting/idempotency integrity must stay green. Don't silently drop the accounting work — relocate it, don't delete it.
4. **Regression guard.** Add a test asserting a single booking completes within a tight time budget (or, better, that booking emits O(1) postings and does NOT trigger a full period-close). So this can't silently regress as the store grows.
