## 2. The cell-data-requirement contract (the BA-210-specific input)

Cell population is **driven by the typed contract**, not hand-coded line logic:

- **Schema:** `prototype/v2-core/regulatory-returns/cell-contract.ts` (the Zod `ReturnCellContractSchema`).
- **BA 210 instance:** `prototype/v2-core/regulatory-returns/ba210-contract.json` (7 527 cells), loaded + validated via `return-contracts.ts` → `loadReturnContract("BA210")`. Machine-generated by `gen-return-contract.py BA210` (an entry for EVERY XSD leaf cell).

### 2.1 Product-attribute requirements — the LEX binding (Phase C batch 2)

BA 210 carries the **richest** credit product-attribute set, because LEX aggregates exposures by (connected) counterparty. The **distinct `required:true` attributes BA 210 obliges** on `prd:bank:credit:loan` are:

| Attribute | Why required | Clause |
|---|---|---|
| `counterpartyIdentity` | the `IDType`/ID-number cell cannot aggregate exposures by counterparty without the counterparty's legal identity | SARB reg 26 (LEX); Basel LEX |
| `connectedCounterpartyGroup` | the connected-group flag is the unit of LEX aggregation | SARB reg 26; Basel LEX10 |
| `connectionType` | the connection type (economic / control) binds the connected group | SARB reg 26; Basel LEX10 |
| `exposureType` | the LEX exposure type drives limit + exemption treatment | SARB reg 26; Basel LEX |
| `exposureClass` (asset class) | the asset-class enum cell cannot populate without the exposure's class | Basel CRE20; SARB reg 23(6) / reg 26 |
| `industry` | the industry-concentration dimension | SARB reg 26 |
| `pdBucket` | the IRB watch-list PD-bucket cell | Basel CRE31–CRE36; SARB reg 26 |
| `regulatoryApproach` | STA-vs-IRB LEX sub-form placement | Basel CRE20/CRE30; SARB reg 23(11)–(13) |
| `pdEstimate` / `lgdEstimate` | IRB watch-list inputs | Basel CRE31–CRE36 |

Monetary aggregates merely sliced by an attribute carry it `required:false`. The NPA gate binds on the `required:true` set; the live FX product feeds none of these and is not blocked. The same **honest scope gap** noted in PROC-FIN-BA-200 §2.1 applies (the product-scope schema does not yet model credit attributes → deferred-gap path).

## 3. Cell-population steps (delta on PROC-FIN-BA-01 §6)

For each of the 7 527 cells, the generator:

1. **Reads the contract entry** via `loadReturnContract("BA210")`.
2. **Resolves the value by `derivation.kind`:**
   - `direct` → fold from the **`ba210-large-exposures-fold`** projection — the large-exposures fold over the credit-exposure register (per-counterparty exposure) + the **party register** (the connected-counterparty group axis). Values are **projections, never stored** (P1).
   - `sum` / `formula` → evaluate the SARB cell-coordinate expression over resolved constituents.
3. **Honours status:** all BA 210 cells are `status: licence-day-data`. The exposure register + party register exist as substrate, but the bank has **no real exposures or counterparties pre-licence-day**; there are no large exposures to aggregate yet. The product-attribute `dataRequirements` bind now.

> **Currency (P5).** Exposure amounts are reported in the functional currency, resolved from reference data, never hard-coded.

## 4. XSD validation before submission (BA-210-specific hard gate)

**Before** four-eyes review, the generated BA 210 instance MUST validate against `BA210.xsd`:

1. Serialise the populated cells into the BA 210 upload XML (the LEX / watch-list / related-party sub-form envelopes; `Monetary1000` + `Number (19,2)` wrappers; the credit-enum code values).
2. Validate against `Regulations/SARB-PA/ba-returns/schemas/BA210.zip → BA210.xsd`.
3. **Fail-closed (Engineering Charter cmd 2):** an XSD-invalid instance is not eligible for review or submission.

In addition to the build-time completeness guarantee enforced by `recon:ba-return-cell-contract`.

## 5. Reconciliation invariants (BA-210-specific)

| Invariant | Assertion |
|---|---|
| **LEX aggregation by connected counterparty** | Each counterparty-group large-exposure line equals the sum of the exposures of every member of the **connected-counterparty group** (per `connectedCounterpartyGroup` + `connectionType`), de-duplicated across facilities. An exposure counted against the wrong group, or double-counted, is a control failure. |
| **Large-exposure limit** | The aggregate exposure to a single counterparty / connected group, expressed against qualifying capital, must be flagged where it breaches the reg 26 large-exposure limit; a breach not flagged on the watch-list is a control failure. |
| **Exposure ties to BA 200** | The total credit exposure aggregated here must reconcile to the BA 200 total credit exposure (same underlying credit-exposure register); a divergence is a control failure. |
| **Related-party completeness** | Every exposure to a related party (significant shareholder, director, senior management, associate) appears on the `BA210_RP` sub-form per the `exposureType` classification. |
| **Trace-to-source** | Every populated cell traces to its `ba210-large-exposures-fold` source; no value without a source (P1/P2). |
